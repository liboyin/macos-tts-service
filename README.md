# Clipboard TTS App

Native macOS menu bar app (Swift/SwiftUI, macOS 13+) that reads clipboard text aloud through OpenAI-compatible TTS APIs or Google Gemini's own streaming speech endpoint. No external Swift dependencies; uses only Apple frameworks (AVAudioEngine, URLSession, NSPasteboard).

```
Sources/

  Managers/
    AudioPlayerManager.swift
    TextExtractionManager.swift
    CallbackAuthority.swift     # the lock spanning delivery authorization and revocation
    DeferredClipboardAction.swift # ownership of the menu's pending deferred clipboard read
    TTSNetworkManager.swift     # request settings, state publication, response delegate entry
    TTSNetworkManager+RequestLifecycle.swift # starting, retrying, replacing, and stopping a request
    TTSNetworkManager+Requests.swift        # endpoint and request-body construction
    TTSNetworkManager+GeminiStreaming.swift # Gemini SSE parsing and audio delivery
    TTSNetworkManager+Failures.swift        # task completion and sanitized failure text
    TTSNetworkManager+Metadata.swift        # guarded model discovery, voice catalogs
```

## Architecture

- **UI**: SwiftUI `MenuBarExtra` for playback controls; a separate `Window` hosts settings to keep the dropdown focused on play/pause/progress/speed. The settings window includes an endpoint test action and an About control that opens macOS's standard panel with the app bundle's name and marketing version; its credits point to the bundled `LICENSE` (AGPL-3.0). It also offers the migration retry described under Settings below, which appears only while a saved key is still unsecured. Every Settings action renders through `SettingsActionButton`, an `NSViewRepresentable` wrapping AppKit's standard rounded push button, because SwiftUI's own `Button` draws itself without backing an `NSView` and so leaves a hosted regression no control to press and no accessibility tree to search; `.fixedSize()` keeps Test Voice hugging its title, which is how `.buttonStyle(.bordered)` laid it out.
- **Audio**: `AVAudioEngine` + `AVAudioPlayerNode` (not `AVPlayer`) so playback speed can be adjusted via `AVAudioUnitTimePitch` without altering pitch. The serialized count of complete 16-bit PCM frames is the source of truth for both buffered duration and seek boundaries—never a sum of per-chunk floating-point durations. The first playable frame of each stream starts one 0.1-second automatic-playback prebuffer window; later packets continue scheduling during that window without moving its deadline. The delayed action is generation-bound, so stopping, replacing a stream, or rebuilding the format cannot restart old audio; any pause of that stream — the menu's Pause or the progress timer's own pause at the buffered end — and a seek to the current end each revoke its pending start, which leaves Play free to resume that stream and leaves a later stream's own deadline untouched. Pausing revokes only that pending start, never the stream itself: it leaves the scheduling generation in place, so PCM arriving while the user is paused keeps buffering and is there to hear on Resume. Seek-related node operations and buffered-data reads share the audio-buffer queue. Playback starts a repeating 0.1-second driver and stops it again with the playback it reports; each tick reads the node's rendered position and publishes the position it implies within one main-queue turn, so a position rendered before a seek is never added to the offset that seek installed, and a tick that reads no position leaves the published one alone. Seeking to the exact end stops playback while retaining audio for replay from zero.
- **Text**: `TextExtractionManager` reads through an injected, read-only pasteboard adapter; the production adapter uses `NSPasteboard.general`. The menu-bar flow deactivates the app and defers the read by 0.2 seconds before starting TTS; because a Services request or a second click can claim the pipeline inside that window, the deferred action revalidates the complete idle condition — no stream, no retained buffer, and a startable audio graph — immediately before it reads the clipboard or changes any generation. It also requires the request generation it captured when scheduled to be unchanged, which is the part published state cannot express: a request that has already finished can still have accepted audio in flight, so both flags read idle while the pipeline is not that attempt's to take, and speaking there would revoke the audio the user is about to hear. That generation advances whenever anything — a Services request, Settings' Test Voice, a Clear Buffer click, a replacement — starts or stops a request, so every one of them makes a waiting attempt stale. `DeferredClipboardAction` then drops every attempt a later click superseded, which is what keeps one burst of clicks to a single pasteboard read even when the clipboard holds nothing to speak and no request records that the pipeline changed hands. A refusal that click has to report — today only the OpenAI input limit below — goes through the injected `MenuAlertPresenting`, which owns both returning the app to the foreground the click deactivated and running the modal panel, so the alert cannot open behind whatever the user is reading and a test substitutes one double instead of activating a host or showing a panel nothing would dismiss.
- **Network**: `URLSession` streams OpenAI-compatible and Custom raw PCM chunks directly. Gemini uses the documented [Generate Content streaming endpoint](https://ai.google.dev/api/generate-content), `:streamGenerateContent?alt=sse`, with `x-goog-api-key` authentication; its request-owned parser accepts LF and CRLF Server-Sent Events, waits for a complete base64 `inlineData` event, and forwards playable 16-bit PCM frames before task completion. Each task captures its provider, endpoint, credentials, request inputs, decoder, and incremental parsing state at creation; later settings changes apply only to the next request. Model and voice metadata maintain independent request state and generation tokens; only metadata for the still-selected provider and endpoint may update the UI. Only model discovery issues a request, and so is the only half with a task to cancel; a voice catalog is a documented constant that still travels the guarded token path, because its publication is asynchronous and a provider switch in that window must invalidate it. The manager never infers a provider from an endpoint: `updateSettings` requires the caller to name one, so the identity it tags a list with is always one a provider form can match. Each published list also carries the provider its request was made for, so a surface never offers a list belonging to another provider: Settings renders a newly selected provider's saved model and voice one render before its `onChange` resynchronizes the manager, and that recorded identity is what makes the render refuse the list it is still holding. Cancellation limits unnecessary work but is not a freshness guarantee: a completion must still match its active request token. Metadata source identity includes both the selected provider and endpoint, because multiple Custom endpoints use the same OpenAI-compatible transport. A delegate callback validates and records task state under a private serial queue, then enqueues its audio handoff on a second serial queue while the state lock is still held; PCM therefore reaches handlers in accepted callback order. Immediately before calling the handler, the delivery queue rechecks its request generation under the state queue: this revokes handoffs still waiting for that check, while normal completion leaves already accepted audio authorized. A separate recursive callback-authority lock holds that recheck through the complete client callback and generation revocation, so a stop or replacement cannot return while a revoked handoff could begin. Advancing that generation is separate from publishing request state, so a caller that must not touch the main queue can revoke delivery without queuing a `@Published` update. Paths that need both locks acquire callback authority before request state; when a Gemini event makes the stream fatal, it advances the generation under request state before waiting for callback authority, so PCM queued earlier in that same delegate callback is also rejected. Handlers remain outside the state lock and may synchronously stop or replace their stream; a stop or replacement on another thread waits for an in-progress handler to return. Because `@Published` notifies observers before storing a value, request-state publications track nested updates and defer observer-triggered replacement requests until the outermost update finishes. Invalid configuration, encoding, HTTP, transport, empty or malformed provider-audio, and provider-declared early-stop failures publish a short, application-owned message in the menu bar; provider response bodies are never rendered, and a new request or Clear Buffer clears the message. The one exception is Gemini's documented transient server error, which is retried once before anything is published (see Design Assumptions). Minimizing Time-To-First-Byte is a primary design goal.
- **Settings**: API keys are generic-password Keychain items under the stable `com.clipboardtts.api-keys` service, one account per provider. `SettingsKeys` owns only persisted preferences plus the three temporary plaintext names used to migrate existing installs. Migration removes a legacy value only after Keychain accepts the write; a failure preserves it and presents Keychain-access guidance. If both stores contain a key, the existing Keychain value wins, preventing stale plaintext from overwriting a newer saved credential. That guidance is actionable where it appears: while a legacy value is still present, Settings offers **Retry Securing Saved Keys**, the only rerun of that migration outside creating a manager, so recovering from a transient Keychain failure does not require relaunching. It reruns against the same injected secret store and preferences the app migrated at startup — `SettingsView.init` takes that `UserDefaults` without a default value, because a hosted or otherwise private startup domain is not `UserDefaults.standard`. Which providers are still pending comes from the retained legacy values themselves rather than a rendered message or a launch-time list, so a reopened window recomputes it; a provider that fails again keeps its plaintext value and its guidance, while one that succeeds hands back the value it secured for the form to adopt and give to future requests. Nothing reads storage a second time to learn that value: the plaintext copy is gone by then, so a store that failed again in that window would otherwise retire the recovery action while leaving the app with no credential at all. The form reports one storage failure at a time but remembers them per provider, so the line on screen is never the whole state: resolving a provider — by that retry or by the user's own edit — withdraws only that provider's message and then names the next key still unreadable or unsaved rather than falling silent, in provider order, preferring a refused edit over that same provider's older read failure because it is the attempt the user just made. Saving or clearing a key retires that provider's plaintext copy as completely as securing it does — the user's own edit is the newer statement of what the credential is, so nothing here or on a later launch can restore a key they replaced or withdrew — and it withdraws that provider's recovery action and menu-bar warning with it. Only a write the store confirmed does this; a refused edit leaves the plaintext exactly where it was. The startup warning in the menu bar is withdrawn once nothing is pending and renamed to the provider still pending otherwise — but only while it is still the message on screen, because a request that published or cleared that line since owns it, and an unresolved migration stays visible in Settings either way.
- **Services**: The macOS right-click "Speak Selected Text with Clipboard TTS" service posts a notification handled by `ServicesCoordinator`, which lives for the whole app lifetime (created in `ClipboardTTSApp.init`). The observer explicitly hands the whole playback-start action to the main actor because notifications can be posted from any thread. This is deliberately *not* in `MenuBarView`: `MenuBarExtra(.window)` builds its body only when the dropdown is first opened, so a view-hosted observer would drop the service until then.

## Design Assumptions

- **OpenAI-compatible endpoints**: Local TTS engines must expose `/v1/audio/speech`. Cloud APIs that differ (e.g. Google Gemini) get dedicated payload formatters.
- **Custom provider contract**: Custom endpoints use the OpenAI-compatible speech payload. Users must configure a non-whitespace model and voice; every Custom request includes both values with `input` and PCM `response_format`. As with OpenAI, a successful response must contain at least one complete 16-bit PCM frame; otherwise the app reports a no-playable-audio failure. Every endpoint that carries the saved key — speech and model discovery alike — must use HTTPS, or plain HTTP only to a loopback literal (`localhost`, the IPv4 `127.0.0.0/8` block, or `::1`), so a local engine that has no certificate to present stays usable while a cleartext remote endpoint is refused before a request or credential exists. This is the app's own contract rather than a reliance on Application Transport Security, which the app does not configure, and it matches the parsed host against those literals only: a private-network address, a name that merely resolves locally, and an ambiguous numeric or percent-encoded form are all refused, because the endpoint alone cannot say where that traffic ends up. Because URLSession follows redirects itself, and a 307 or 308 replays the original method and body at whatever endpoint the response names, a redirect target answers to the same rule before it is followed. A refused speech request — endpoint or redirect — publishes a short configuration failure that echoes neither the endpoint nor the key, and a refused redirect reports that failure rather than the provider's redirect status; a refused discovery request is silent, as every other metadata failure is. Settings asks for discovery only on OpenAI's fixed HTTPS endpoint, so no configuration it can produce reaches that refusal; the rule is kept on the discovery path as defense in depth for a later caller that derives the URL from a saved value, and its tests say so where they set up a configuration Settings cannot.
- **PCM sample rate**: OpenAI and Gemini audio always uses the fixed 24,000 Hz mono Int16 format. Custom endpoints default to 24,000 Hz and may select any finite rate from 8,000 through 48,000 Hz in Settings; applying a changed rate discards the prior buffer before rebuilding the audio graph. The visible Custom draft is the authoritative requested rate for validation and retry, while persistence changes only after a successful graph update. Invalid draft edits do not replace the saved last-known-good rate, and a corrupt legacy value blocks new speech until it is corrected rather than silently decoding at 24 kHz.
- **Provider authentication**: OpenAI and Custom requests carry their saved key in `Authorization: Bearer`; native Gemini requests use the raw saved key in `x-goog-api-key`. Keys are never appended to URLs or included in app-owned errors.
- **Gemini audio**: The supported Gemini 3.1 TTS preview model streams base64-encoded `inlineData` through Server-Sent Events. The app treats malformed/provider-error events and streams that finish without playable audio as a sanitized no-playable-audio failure; valid non-audio metadata events that declare no finish reason are ignored, and valid Gemini output is 24-kHz mono, 16-bit PCM.
- **Gemini early stop**: Each decoded event also records the `candidates[0].finishReason` it declares, and a completed stream whose most recently declared reason is not `STOP` publishes "The TTS service stopped early. The speech that arrived is incomplete. Please try again." That message names the truncation rather than reusing the no-playable-audio text because the PCM already handed to the player stays playable — the user can hear the speech it describes — and it is checked after the refused-redirect, HTTP-status, malformed-stream, transport-error, and incomplete-event outcomes but before the PCM-frame check, so a truncation that arrived with no audio at all still explains itself. Only an explicit reason counts: a candidate-free metadata event, a candidate omitting the field, and a `finishReason` of a non-string type all declare nothing and never erase a reason an earlier candidate declared, because a stream may simply end without final metadata and a provider schema change must leave the remaining completion checks in charge rather than revoke audible speech. The rule exists because Google's `:streamGenerateContent?alt=sse` endpoint has an open defect for `gemini-3.1-flash-tts-preview` that truncates audio past roughly 60–70 seconds with `finishReason: OTHER` under HTTP 200 while the identical body to non-streaming `:generateContent` returns `STOP` and complete audio; a Google engineer confirmed reproduction on 2026-06-23 and the thread was still unresolved when re-checked on 2026-09-03 ([report](https://discuss.ai.google.dev/t/gemini-3-1-flash-tts-preview-streamgeneratecontent-truncates-audio-finishreason-other-past-60s-while-generatecontent-non-streaming-works/169063)). The app deliberately neither chunks the request text nor moves Gemini to the non-streaming endpoint; it reports the loss instead. This is separate from the bounded HTTP 500 retry below, which is never extended to a non-`STOP` finish reason.
- **Gemini transient failure**: Google documents that the model occasionally returns text tokens instead of audio, that the server then fails the request with HTTP 500, and that applications should retry those automatically ([limitations](https://ai.google.dev/gemini-api/docs/generate-content/speech-generation), re-verified 2026-08-17 against the Generate Content variant the app's endpoint uses). A Gemini speech request that finishes with exactly that — status 500 and no transport error — is therefore retried once, silently. The retry continues the same logical request rather than starting a new one: it replays the URL, headers, and body its first attempt sent instead of rebuilding them from settings the user may have edited meanwhile, keeps the same handler and cancellation generation, and publishes no state of its own, so the menu bar stays truthfully streaming across the handoff and a stop, Clear Buffer, or replacement in that window prevents the retry from starting at all. Because a 500 response is never parsed for audio, the retry cannot duplicate anything already delivered. Recovery is bounded to that single extra attempt: a second 500 publishes the sanitized HTTP failure once and finishes normally. Nothing else is retried. Another provider, another status, a transport error accompanying the response, a refused redirect, malformed SSE, and a stream that ended without playable audio each publish their failure after one attempt, because those describe something the user or the network has to resolve and repeating them only delays the guidance.
- **OpenAI input limit**: OpenAI documents one maximum for the `input` of every model its Speech API accepts — 4,096 characters, re-verified 2026-09-03 against the [create speech reference](https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create). The menu's **Speak Copied Text** click therefore refuses longer clipboard text locally rather than spending a request that can only fail, and whose failure would reach the user as the same generic HTTP message every other error produces. The check runs inside the deferred clipboard action, after the read and the staleness revalidation and before any stream starts, so a superseded attempt neither speaks nor raises a dialog; it makes no provider call and leaves every accepted request on its existing one-request path. "Characters" is counted as Unicode scalars because the documentation names no Unicode unit: grapheme clusters would let text the provider rejects through, while UTF-16 code units or UTF-8 bytes would refuse non-Latin text it accepts, and a false refusal is the costlier error because no later provider response can undo it. The rule is scoped to the built-in OpenAI provider, read from the manager's persisted provider identity rather than a second endpoint inference beside it — Gemini documents no such maximum, and a Custom endpoint's limits belong to whoever runs it, whose default base URL is the same string as OpenAI's fixed endpoint. Services and Settings' Test Voice keep their current behavior, which is why the rule lives in the menu view and not in `streamTTS`. A refusal presents the app-owned pop-up "Copied text is too long" / "OpenAI accepts at most 4,096 characters per request. The copied text is N characters. Copy a shorter passage and try again." — counts grouped in `en_US` so the digits match the English sentence the app ships, and a length is the only thing it reports about the clipboard — and does not also publish through `lastError`, whose inline rendering would state the same outcome twice. The provider is the one selected when the click was revalidated: a provider the user switches inside the request's own start window is out of scope, because a settings edit advances no request generation and `streamTTS` snapshots its own settings when the request starts.
- **Provider normalization**: An unknown persisted provider value is normalized to OpenAI and its fixed endpoint before any request is built. This fails safely instead of pairing a key with an arbitrary Custom endpoint.
- **Voice metadata**: Voice selection belongs to Settings alone. The menu-bar drop-down is playback control — speak/clear, play/pause, progress, speed — and neither offers nor displays the configured voice, so the voice lives beside the model and API key that decide what it means. Settings fetches its own model and voice suggestions when it opens, which is why removing the menu's picker cost no lookup: `SettingsView.onAppear` already calls `syncSettings()`. OpenAI does not expose a built-in voice-discovery endpoint for speech, so its suggestions use the provider-authoritative list in the official [Text-to-Speech guide](https://developers.openai.com/api/docs/guides/text-to-speech#voice-options): `tts-1` and `tts-1-hd` offer alloy, ash, coral, echo, fable, onyx, nova, sage, and shimmer; other configured OpenAI TTS models offer those nine plus ballad, verse, marin, and cedar. Gemini documents no discovery endpoint either, so `TTSNetworkManager+Metadata.swift` holds the complete voice list from the official [speech-generation guide](https://ai.google.dev/gemini-api/docs/speech-generation) — 30 voices as verified on 2026-08-20 — as a single production constant published through the freshness-guarded metadata path. Google changing the documented set is therefore a source change: re-verify the constant against that guide's "Voice options" table, in its order, rather than adding voices from another provider or a discovery request Gemini does not offer. A Custom endpoint has no discovery contract; its voice is whatever Settings has configured, and Settings does not ask for one. No supported provider offers voice discovery, so the app makes no voice request at all and holds no decoder for a voice response; reinstating one is a provider-contract change, not a refactor. A model or voice the current catalog does not list — typed by the user, or saved before the documented set changed — is kept exactly as configured and offered by that provider's Settings picker alongside the catalog it can be corrected from, because SwiftUI documents a picker whose selection has no matching tag as undefined and normalizing the value would speak in one the user never chose.
- **External toolchain**: `xcodegen` and `swiftlint` are user-managed; the app does not install or modify them.

## Build & Test

Regenerate Xcode project after editing `project.yml` or adding/removing source or test files, so Xcode discovers the current file set:
```
xcodegen generate
```

Build:
```
xcodebuild -project ClipboardTTSApp.xcodeproj -scheme ClipboardTTSApp -configuration Debug build
```

Both targets remain in Swift 5 language mode, but `project.yml` enables complete strict-concurrency
checking for each of them, and the setting sits on each target rather than on a command, so anything
that builds a target checks it: `./check-coverage.sh` builds the test bundle and, through the test
target's declared dependency, the app target as well, while the explicit app build above remains a
required gate in its own right. Keep queue-owned request/audio buffers behind their explicit serial
queues, and hand UI, AppKit, and Services work to the main actor; `@unchecked Sendable` is reserved
for the URL-session delegate bridge and documented confinement invariants. An incremental build
reports only the file batches it recompiled, so clear the derived data before concluding that a
target is warning-free.

For streaming requests, accept, parse, and account for provider data while holding request-state
ownership; defer only the user audio handler to the ordered delivery queue. Completion must never
be able to clear request state ahead of an accepted final Gemini event. Handlers must not run under
the request-state queue, because they are allowed to synchronously stop or replace their stream.

Run tests and check the line coverage of `Sources/Managers/`:
```
./check-coverage.sh
```

Because XCTest launches the hosted macOS app before XCTest `setUp()`, `ClipboardTTSApp.init` detects that host and builds a separate dependency graph: a fresh process-private defaults suite and an `InMemorySecretStore`. Its startup manager reads and migrates only that owned state, so it cannot read, migrate, delete, or block on the installed app's settings or Keychain. `SettingsView` binds every one of its `@AppStorage` properties to the domain it is handed, so the window that graph opens displays and writes the same private domain rather than the process default store the property-wrapper attribute would otherwise resolve to. Production startup continues to use `UserDefaults.standard` and `KeychainSecretStore`; `AppStartupDependencies.make` is the supported injection seam for regression coverage.

Every initializer reached from that startup graph must receive the selected defaults explicitly; a default parameter on a downstream migration or manager is not sufficient isolation. Startup regressions must exercise the automatic hosted branch as well as injected branches: seed conspicuous values into an owned store standing in for a developer installation, then prove the automatic graph uses neither it nor `UserDefaults.standard` and selects an `InMemorySecretStore`, leaving those values unchanged. That last check compares the domain by identity rather than reading it, because seeding the installed app's own settings to prove they were left alone is the access these regressions exist to forbid. Do not test a Keychain regression by running a Keychain-backed hosted startup—the expected failure can block on macOS; the baseline must prove it selects the in-memory store instead. Any defaults a regression seeds itself must live in memory rather than in a `UserDefaults(suiteName:)` suite: emptying a suite's persistent domain does not delete it, and `cfprefsd` rewrites the suite's plist into `~/Library/Preferences` when the hosted test process exits, so a seeded suite left one file behind per run. The automatic hosted branch keeps the production fresh suite, which materializes no file precisely because nothing writes through it. A test-owned `UserDefaults` subclass must keep its values out of the app's own domain as well as off disk. No regression asserts this by listing the developer's preferences directory: reading their state to prove it was left alone is the access this storage exists to remove, and Foundation persists asynchronously, so such a check could pass before a plist appeared. What establishes that the accessors answer from owned memory is the aggregate view — owned storage reads back exactly what its owner set and nothing else — with a separately owned store beside it proving that one owner's seed reaches no other.

The unit-test bundle is hosted inside the app, so `UserDefaults.standard` in a test is the real app's defaults domain. No test reads or writes it: every regression that states a setting creates its own storage with `makeOwnedDefaults` (`Tests/OwnedDefaults.swift`) and hands it to the manager, the hosted form, or the migration under test, so there is nothing to clear beforehand and nothing to restore afterwards — the storage is discarded with the test that made it. `TestNetworkFactory.makeManager` gives each manager fresh owned storage unless the caller passes its own, which is how a test that drives both a manager and a hosted form puts them in one domain. A behavioural assertion passes whichever domain the code under test was given, because what it checks is the behaviour rather than the domain — only the two isolation tests below name it, comparing owned storage and the hosted startup graph against it by identity — so injecting the process domain at an ordinary call site would pass that call site's own assertions. Three things keep that from happening, in descending order of strength. No settings API in `Sources` defaults to `.standard` any more — `AppStartupDependencies.make` is the single composition root that names it — so omitting a store fails to compile rather than silently selecting the developer's. `InMemoryDefaults` owns the inherited half of `UserDefaults` as well as the three accessors it overrides. Building the superclass against a suite of its own redirects the receiver-relative half away from the app's domain, but not the surfaces addressed another way: the aggregate view over the whole search list, the registration and volatile domains Foundation shares process-wide, forced values, and any member taking a domain *name* — which could be the app's own. Each of those is overridden to answer for its owner instead. Last, the `process_default_settings_store` lint rule fails the gate on the named routes into that domain from `Sources/` and `Tests/` alike — leaving `AppStartupDependencies.make`, which carries the only two Sources-side disables, as the single place production names it, while the isolation suite carries line-scoped disables of its own for the deliberate probes that have to name what they prove stayed clean — and a companion `test_owned_settings_storage` rule rejects the two spellings that are legitimate in production but not in a test: a test-local `@AppStorage`, and a `UserDefaults` subclass whose superclass is built against the default search list. The named routes are: `UserDefaults.standard` in any spelling, the `defaults:` shorthand, constructing a `UserDefaults`, `NSUserDefaultsController`, and `CFPreferences`. That rule is a regex, so treat it as a guard against reintroducing the habit rather than a proof — a spliced comment or a type alias still gets past it. Naming `UserDefaults.standard` without accessing it stays legal behind an explicit disable, because a startup regression and the isolation suite compare that domain by identity to prove owned storage is not it. That storage is memory rather than a `UserDefaults(suiteName:)` suite, and it announces its changes through KVO because `@AppStorage` observes its store that way; a store that stayed silent would leave a hosted form ignoring every write made from outside it, `HostedSettings.selectProvider` included. What `MockURLProtocolTestCase` still owns is the network lifecycle: it serializes mock-network tests and releases the next one only after its sessions, protocol loads, manager initialization, and factory-owned audio-delivery queues are quiescent. Scope shutdown first revokes each factory manager's pending delivery generation, then drains every registered serial delivery queue before releasing the next mock test. Revocation runs in two halves. The half that advances the delivery generation waits for an in-flight client handler to return, so it runs off the tearing-down thread under the same deadline as the rest of shutdown; an owner it cannot release inside that deadline reports a non-quiescent scope rather than blocking, and the off-main recovery path finishes it. The second half then runs on the tearing-down thread and advances the generation once more, which makes the first half's queued publications stale so they cannot land in a later test. When that thread is main — every ordinary teardown — the second half also reads and restores the owner's main-queue-confined terminal state without a hop, which is what lets a test assert `lastError` after quiescence. Timeout recovery runs off-main, so revocation must not synchronously wait for the main queue. That recovery path neither reads nor restores terminal state; it advances the delivery generation through the manager's non-publishing `revokeActiveRequest()` rather than `stopStreaming()`, so it queues nothing to main and cannot erase state a later test is reading. Recovery is bounded as well, because it holds the mock-test gate closed while it waits on whatever the deadline gave up on — usually a client handler that has not returned, but equally an outstanding session, protocol load, manager construction, or delivery-queue drain. A scope it cannot revoke inside that bound stays registered — an owner nobody revoked can still deliver — and the run ends immediately with that scope's identifier instead of releasing the gate to a test that would inherit a live callback owner. That `NSCondition` remains the sole mutual-exclusion and wait/broadcast primitive for scope state; the registry it guards sits in a checked-`Sendable` `OSAllocatedUnfairLock` only because a manual lock is invisible to strict concurrency, and it is entered exclusively while the condition is held, so a shutdown step must keep taking the condition rather than treat that box as its lock. `Tests/MockURLProtocolScopeState.swift` holds the shape of a scope and its quiescence rule, which is why those types are internal rather than file-private.

Network tests must create managers and sessions through `TestNetworkFactory`, which routes all requests through `MockURLProtocol` with an immutable per-test identifier. The factory atomically claims manager construction before initialization can read settings, so a scope cannot close while legacy-key migration is still running. `MockURLProtocolTestCase` serializes those tests, invalidates their sessions and drains active protocol loads before releasing the next test, clears the installed response handler in setup and teardown, and fails a test that has an undeclared request without a handler; an explicitly declared unhandled request fails locally with a URL-loading error. Clipboard tests inject `FakePasteboardReader` and never modify the user's shared pasteboard.

Network-state tests wait for the relevant published terminal state (`lastError` and `isStreaming`) or an explicit mock-protocol event; install that observation before releasing any action that can complete the request, so a successful terminal publication cannot race ahead of the test. Successful terminal-state assertions must also observe an active request. Every terminal-state assertion, success or failure, must in addition observe a publication caused after its action started: Combine replays the manager's current state on subscription, so a matching error from an earlier request would otherwise settle an assertion whose action never ran a request. A timestamp is not enough, because the manager publishes off-main work through `DispatchQueue.main.async`: the helper first drains the main queue, so a publication an earlier request had already queued lands in the replayed value instead of masquerading as the action's own terminal state. If that drain cannot complete within the assertion's timeout the helper fails rather than proceeding, because an undrained queue can still hide a stale publication. Call the helper from the main thread: it writes its observation flags on the caller's thread and reads them in a sink Combine delivers on the main queue, so it fails an off-main call site instead of racing them. That boundary covers state that already exists or is already queued when the assertion starts; a still-live earlier request that publishes concurrently with the action remains indistinguishable from it here, and is covered instead by the generation-ownership tests. Pass the state-changing event to the helper's action rather than performing it beforehand. A configuration or encoding failure published synchronously during the action still qualifies, so a failure need not pass through `isStreaming == true`. `awaitTerminalState` returns that same outcome without failing the test, which is how a negative regression proves a pre-action value cannot settle; a violated precondition still fails closed: an off-main call site or an unestablished drain fails the test as well as returning `false`, so that `false` is never a silent verdict. Do not use elapsed-time polling to infer that an asynchronous request completed.

Concurrency tests use a controllable serial delivery queue and semaphores to force completion,
handler, and callback ordering deterministically. Use distinct PCM chunks when asserting order;
byte totals alone cannot reveal reordering. State a callback on another thread writes and the test
body reads belongs in `LockedValue` rather than an `NSLock` declared beside a `var`, because the
compiler cannot tell that pair's guarded write from a race; take a read-modify-write whose result
decides the callback's next step in one `withValue` so it stays a single critical section. A Services test that posts from a background queue must
exercise the production main-action executor and observe the action on main, rather than supplying
an executor that itself performs the hop.

For focused XCTest runs, use the `ClipboardTTSAppTests` scheme (the generated project has no separate app-test scheme). A test that verifies a SwiftUI `.onAppear` action or an `NSViewRepresentable` control, or that reaches any lifecycle-managed `@State` or `@StateObject`, must host the view in `NSHostingView` and lay it out; constructing the view value alone neither runs its lifecycle action nor installs that storage, and SwiftUI then builds a fresh `@StateObject` on every access and discards `@State` writes, so such a test exercises different state identity from the production window and can pass for a reason production never reproduces. Do not wrap that test host in an `NSWindow`: AppKit window teardown can outlive the test and crash the hosted process. Release the hosting view and drain one main-queue turn before `MockURLProtocolTestCase` invalidates its session, so deferred Settings observers cannot create work after their test scope closes. `Tests/HostedSettings.swift` owns that lifecycle for Settings and is how its tests drive the form; it and the shared model/voice host are `@MainActor`, as is every test method that uses either, because `NSHostingView` and the AppKit controls they build are main-actor isolated and the honest boundary is that isolation rather than an escape at each call site. In a windowless host SwiftUI backs its text fields with AppKit controls but draws its buttons and list rows itself, so an action is reached by clicking its `SettingsActionButton` — and one the form renders conditionally is proven absent by asking the host whether it renders that title, since clicking a missing control fails instead — a provider is selected by writing the sidebar list's `@AppStorage` key into the store the form was mounted with, which is why `HostedSettings` keeps that store rather than reaching for a process-wide one, and a text edit is delivered by assigning `stringValue` and posting `controlTextDidChange` to the SwiftUI coordinator that owns the field. Neither a placeholder nor an accessibility identifier survives into that AppKit layer, so a field is addressed by its position among the form's fields and every edit states the text it expects to find there; a reordered form then fails by name instead of silently editing a different field. Opening Settings on OpenAI also fetches its model and voice suggestions, so a hosted test that must prove no speech request started has to distinguish the speech endpoint rather than reject every request. A suggestion control is read back as the choices it offers together with the choice it displays, which is how a test proves that a rendered picker's selection is one of its own tags. The shared model and voice fields have a host of their own because a provider switch renders them once before `onChange` resynchronizes the manager and SwiftUI commits no AppKit state for that render: by the time the hosted form can be inspected, the manager has been resynchronized and its stale lists cleared, so only rendering those fields directly holds that configuration still.

A test that proves a helper fails must scope its `XCTExpectFailure` with an `XCTExpectedFailure.Options` `issueMatcher`; the unfiltered form accepts any later issue from any thread. Matching the expected diagnostic couples the test to that wording; that is the intended trade-off, since rewording then fails the test instead of silently accepting something else.

A test that calls into the code under test from another queue must own that queue and establish quiescence unconditionally after its bounded wait — a serial queue plus a trailing `sync {}` barrier. Fulfilment is not quiescence: an expired wait leaves the dispatched work runnable, free to record failures after the expectation window closed and to write results the assertions are already reading.

Audio-manager tests that exercise the 0.1-second automatic-playback prebuffer inject a controllable scheduler and wait for the manager's explicit audio-queue processing or state-publication hook. Progress-tick tests state the rendered position the manager reads and keep its progress timer out of every run loop, so they fire that timer, and with it the callback the manager gave it, where they want a tick rather than waiting a cadence out; they hold the prebuffer's deferred start until they release it themselves. They must assert the queued callback before running it; do not use a sleep or a real deadline as a synchronization boundary. This keeps packet ordering, cancellation, and delayed-start tests deterministic. Menu tests that must own when the deferred clipboard read runs inject a `DeferredClipboardAction` scheduler for the same reason, and assert the delay it was asked for rather than waiting it out. They also inject a `MenuAlertPresenting` recorder: no test may take the production presenter, which activates the app and runs a modal panel nothing in a test would dismiss, so `makeMenu` defaults to the recorder and `MenuBarView` itself declares no default. A menu test that must prove exactly one request started counts the manager's request generation, drained until it settles, rather than mock-handler invocations: a duplicate request replaces the first, whose task can be cancelled before its handler ever runs, and a start the manager defers while publishing state is re-queued onto the main queue, so handler fulfilments observe a duplicate only sometimes while the generation observes it always. `AppKitMenuAlertPresenter` is consequently the one production type the suite never executes — it appears at 0% in the exempt `Sources/Views/` report — because running it would activate the app and block on a panel; what it would show is asserted where the message is built, in `MenuBarView`.
